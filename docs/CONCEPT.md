# PR-Storyboard コンセプト v0.2

> v0.1（初期案）からの検討結果を反映した版。「決定」は合意済み、「提案」は未合意の推奨、「未決」は今後判断が必要な事項。

## 0. 決定事項サマリ

| 論点 | 決定 |
|---|---|
| 主な読み手 | レビュアー（エンジニア） |
| 中核の約束 | 変更の**概要・方針・内容・理由**を効率よく把握させ、レビューをボトルネックにしない。コードを読むかどうかは利用者に委ねる（中立） |
| 表示面 | Web ページ。PR にはリンク付きコメントが届く |
| 実行形態 | 利用者が任意の場所に立てるセルフホストサーバ。Webhook 受信から生成・配信・コメント投稿まで**サーバが全部やる** |
| アーキテクチャ方針 | OSS。インフラ依存を排したシンプル構成（単一コンテナ・DB なし） |
| SCM | MVP は GitHub のみ。SCM アダプタ層は切っておく |
| 生成タイミング | 利用者設定で可変 |
| LLM | **公式 CLI バックエンド（サブスク利用）を主**、API キーはフォールバック |
| 静的解析 | 言語非依存・浅く |
| 閲覧認証 | 設定で選択（none / 署名 URL / GitHub OAuth） |

## 1. プロダクト定義

- **名称**: PR-Storyboard（暫定。§12 参照）
- **タグライン案**: 「コードを読むかは、あなたが決める。」
  - サブ: 「PR の理由・方針・影響を 1 ページで。1 コンテナで動き、手持ちの AI サブスクで回る。」
- **一言定義**: PR ごとに「なぜ・どういう方針で・何を変え・どこに影響し・何が危ないか」を 1 枚の Web ページにまとめ、PR にリンクを届けるセルフホスト型サーバ。

### 1.1 Why（改訂）

- AI によるコード生成で PR の量とサイズが増え、**人間の理解がボトルネック**になっている。
- ボトルネックの正体は「1 行ずつ読むこと」そのものより、**読む前の全体把握**（何のための変更か、どこを読めば良いか、何が危ないか）にかかる時間。
- 本プロダクトはこの「読む前」の時間を削る。精読するか、ざっと見るか、任せるかは**チームと個人の流儀に委ねる**。レビューを省略させる道具でも、強制する道具でもない。

---

## 2. 設計原則

1. **中立**: 「承認してよい」「レビュー不要」といった判定は出さない。出すのは事実とシグナルまで。
2. **事実と AI 推定を分離する**: 依存追加・マイグレーション・設定変更・ノイズ判定などは**決定的処理**で出す。LLM は解釈と文章化のみを担う。UI 上でも「検出（事実）」と「AI 推定」を視覚的に区別し、各主張に根拠（ファイル・hunk）へのリンクを付ける。
3. **読まなくていいものを明示する**: 除外したファイルは隠さず「lockfile 3・スナップショット 12・生成コード 5 を除外」のように件数と理由を見せる。
4. **鮮度を明示する**: ボードはどのコミット（head SHA）に対するものかを常に表示し、古くなったら目立たせる。
5. **シンプルな運用**: 単一コンテナ・DB なし・外部キューなし。状態はファイルだけ。

## 4. ボード構成

1 画面目で「理由・方針・影響・リスク」が掴めることを目標とする。

| # | セクション | 内容 | 出所 |
|---|---|---|---|
| H | ヘッダ | PR タイトル、base…head SHA、生成日時、使用バックエンド、**古さ表示**（新しい push があれば警告） | 事実 |
| 1 | **サマリ** | Why（変更理由）/ 方針（どういうアプローチを選んだか）/ What（何が変わったか）/ 利用者・クライアント影響の有無 | AI 推定 |
| 1b | **PR 説明との乖離** | PR 本文に書かれていない変更、書かれているのに実装されていない変更 | AI 推定（AI 生成 PR で特に効く） |
| 2 | **変更マップ** | モジュール依存グラフ上で変更ノードを色付け（変更前後が分かる差分図）。処理フロー／シーケンス図は該当する場合のみ | グラフ＝事実、フロー図＝AI 推定 |
| 3 | **読むべき箇所** | 本質的な変更を含む上位ファイル（2〜5 件）と選定理由。全ファイルの 1 行要約（折りたたみ）。除外ファイルの件数と理由 | 分類＝事実、要約・順位＝AI 推定 |
| 4 | **リスク・副作用シグナル** | 下表 | 混在（ラベル付き） |

### 4.1 リスク・副作用シグナル

| シグナル | 検出方法 |
|---|---|
| 新規／メジャーアップデートの依存パッケージ | manifest/lockfile の差分解析（決定的） |
| DB スキーマ／マイグレーション変更 | パスパターン＋ファイル種別（決定的） |
| 環境変数・設定ファイル・フィーチャーフラグ | `process.env` / `os.Getenv` 等のパターン、設定ファイルのパス（決定的） |
| CI／デプロイ設定の変更 | `.github/workflows` / Dockerfile / IaC パス（決定的） |
| 認証・権限まわりのパスへの変更 | パスとキーワードのヒューリスティック（決定的） |
| 公開 API／export の追加・削除・シグネチャ変更 | tree-sitter による浅い抽出（決定的） |
| テストの削除・変更規模に対してテストが少ない | 統計（決定的） |
| シークレットらしき文字列 | パターンマッチ（決定的） |
| 過剰実装の兆候 | 実装が 1 つしかない新規抽象、未使用の export、既存依存と機能が重なる新規依存、意図に対して不釣り合いな変更量（事実＋AI 推定） |
| 振る舞い変更なのにテストが追従していない | AI 推定 |

## 5. アーキテクチャ

### 5.1 全体像

```
                ┌──────────────── PR-Storyboard（単一コンテナ）────────────────┐
GitHub ─webhook▶│ Receiver ─▶ Job Runner（プロセス内キュー・同時実行数制限）       │
  ▲   (or poll) │               │                                            │
  │             │               ├─ Collector   : PR 情報・diff・本文・コミット  │
  │             │               ├─ Workspace   : bare mirror + 読み取り専用 worktree │
  │             │               ├─ Analyzer    : 決定的解析（§7）              │
  │             │               ├─ Narrator    : LLM バックエンド（§6）→ JSON  │
  │             │               └─ Store       : /data/{repo}/{pr}/{sha}/board.json │
  │             │                                                             │
  └─comment─────│ Commenter（sticky コメント更新）                              │
                │ Viewer ：board.json を HTML テンプレートで描画 + 認証（§8）   │
                └─────────────────────────────────────────────────────────────┘
```

### 5.2 要点

- **状態は `board.json` だけ**: 生成結果は構造化 JSON で保存し、HTML は閲覧時にテンプレートで描画する。テンプレートを改善すれば過去のボードにも反映される。「単一 HTML としてダウンロード」ボタンで、自己完結 HTML（CSS/JS インライン）も出せる。
- **DB なし**: 一覧やインデックスはファイルシステムの走査で足りる規模を前提にする。ストレージはアダプタ化し、将来 S3 互換にも対応可能にする。
- **再起動に耐える最小限**: キューはメモリ上に持つ。再起動で失われたジョブは、次のイベントかコマンドで再生成される（厳密な永続化はしない）。
- **連続 push 対策**: 同じ PR の古いジョブは新しい push でキャンセルする（debounce）。
- **GitHub App 方式**: 権限は `pull_requests: write`・`contents: read`・`metadata: read` に最小化する。App Manifest フローで「ボタン 1 つで App を作成」できるようにし、導入の手間を減らす。
- **fork PR も扱える**: シークレットは CI ではなくサーバ側にあるため、GitHub Actions の fork 制約（fork からの PR では secrets が使えない）を受けない。
- **受信経路**: webhook（公開 URL が必要）と **polling モード**（N 分ごとに open な PR を確認。社内ネットワークなど外から到達できない環境向け）を選べる。

### 5.3 セキュリティ（必須要件）

- **プロンプトインジェクション前提で設計する**: PR の本文とコードは攻撃者が制御できる入力として扱う。
  - CLI エージェントには**読み取り専用ツールのみ**を許可する（例: Claude Code は `--allowedTools` で Read/Grep/Glob 系に限定、Codex は read-only sandbox）。
  - ワークスペースは使い捨ての worktree に置き、ネットワーク・書き込み・シェル実行は許可しない。環境変数にシークレットを渡さない。
- **LLM の出力は信用しない**: JSON スキーマで検証し、HTML には必ずエスケープして埋め込む。LLM が生成した Mermaid は構文検証とサニタイズを通す（`securityLevel: 'strict'`）。
- 「外部 SaaS にコードを預けない」は正確には「**利用者が選んだ LLM プロバイダ以外の第三者に渡らない**」と表記する。

### 5.4 技術スタック（提案）

- **TypeScript / Node.js**。公式 CLI（claude / codex / gemini）が Node 系であり、コンテナに Node が必要になる。さらに Octokit・web-tree-sitter（WASM）・Mermaid と相性が良いため。
- 配布は Docker イメージ（CLI 同梱版と非同梱版）。

## 6. LLM バックエンド

### 6.1 方針: 公式 CLI を主、API をフォールバック

| 種別 | 例 | 特徴 |
|---|---|---|
| **CLI（主）** | `claude -p` / `codex exec` / `gemini` | サブスクの枠で動く。**エージェントとしてリポジトリの周辺コードを読める**ため、diff だけ渡すより設計意図の推定精度が高い |
| API（フォールバック） | Anthropic / OpenAI / Gemini API | 従量課金。サブスクのレート制限に達したときの退避先。diff のみのモード |

- **認証情報には触れない**: 本プロダクトは CLI を実行するだけで、トークンを読まない・保持しない・転送しない。CLI へのログインは利用者がサーバ上で公式手順で行う。
  - 背景: Anthropic は 2026 年 2 月に、Pro/Max サブスクの OAuth トークンをサードパーティ製品で使うことを明示的に禁止した。そのため「CLI を呼ぶ」方式以外は採らない。
- **規約遵守は利用者の責任**と明記する。特に「1 人のサブスクをチーム共有サーバで使い回す」形態は、各社規約上問題になり得る。ドキュメントで想定形態（個人・小規模チームで、サブスク所有者自身の PR やチーム運用）と注意点を示す。
- **レート制限への対応**: CLI がレート制限で失敗したら、設定に応じて「待って再試行」「API へ切り替え」「スキップしてコメントで通知」を選べるようにする。
- **出力契約**: どのバックエンドでも同じ JSON スキーマで出力させる。CLI ではスキーマを指示したうえで検証し、失敗時は 1 回だけ再試行する。

### 6.2 巨大 PR

- 決定的解析でノイズを除外した後、ファイル群をモジュール単位で分割して要約し、それを統合する（map-reduce）。
- `max_files` / `max_changed_lines` を超える場合は、縮退版（事実のみ・AI 要約なし）を出すか、スキップするかを設定で選べる。

## 7. 決定的解析（言語非依存・浅く）

- **import 抽出**: web-tree-sitter と主要言語向けクエリで行う。クエリがない言語は正規表現にフォールバックする。モジュール（ディレクトリ）単位の依存グラフを作る。
- **manifest 差分**: package.json / lockfile、go.mod、requirements・pyproject、Cargo.toml、Gemfile、pom/gradle など。
- **ノイズ分類**: `.gitattributes` の `linguist-generated` / `linguist-vendored`、`Code generated ... DO NOT EDIT` などのマーカー、lockfile、スナップショット、フィクスチャ、モックのパスパターン。
- **パス規則**: マイグレーション、CI、IaC、設定ファイル、認証関連。
- 利用者は設定で規則を追加・上書きできる。

## 8. 閲覧認証（設定で選択）

| モード | 用途 | 備考 |
|---|---|---|
| `signed-url`（**デフォルト**） | 一般用途 | HMAC 署名付きの推測困難な URL。有効期限は任意。PR コメントを見られる人（＝リポジトリを読める人）がボードを開ける |
| `github-oauth` | 機密性の高いリポジトリ | 閲覧者がそのリポジトリの読み取り権限を持つかを GitHub API で確認する |
| `none` | VPN 内・ローカル | サーバの置き場所で守る前提 |

## 9. 設定

2 層構成にする。サーバ設定（環境変数またはファイル）は認証・バックエンド・ストレージを、リポジトリ設定（`.pr-storyboard.yml`）は生成ポリシーを担う。

```yaml
# .pr-storyboard.yml（例）
language: ja
triggers:
  events: [opened, ready_for_review, synchronize]   # synchronize を外せば push 毎の生成を止められる
  command: /storyboard                               # コメントで手動（再）生成
  label: storyboard                                  # ラベル付与で生成
  debounce_seconds: 120
skip:
  draft: true
  max_changed_lines: 20000
  paths_only: ["docs/**", "**/*.md"]                 # これだけの変更なら生成しない
backend:
  prefer: [claude-cli, codex-cli, anthropic-api]     # 上から順に試す
  on_rate_limit: fallback                            # wait | fallback | skip
noise:
  extra: ["**/__generated__/**"]
risk:
  auth_paths: ["src/auth/**", "src/middleware/session*"]
```

## 10. ポジショニング（改訂）

CodeRabbit も要約・ファイル表・シーケンス図を含む walkthrough コメントを出している。したがって「図があること」は差別化にならない。差別化の軸は次のとおり。

| 軸 | PR-Storyboard | CodeRabbit / PR-Agent 等 |
|---|---|---|
| 目的 | レビュー**前**の全体把握（中立） | レビューそのもの（指摘・提案） |
| 出力 | 専用 Web ページ（折りたたみ・フィルタ・差分図などコメント欄の制約を受けない） | PR コメント／インライン指摘 |
| 信頼性設計 | 事実と AI 推定を分離し、根拠へリンク | 主に LLM 出力 |
| 運用 | セルフホスト 1 コンテナ・DB なし | SaaS 中心（一部セルフホスト可） |
| コスト | **手持ちのサブスク（公式 CLI）で動く** | 席課金 or API 従量 |

- 競合というより**共存**を想定する。インライン指摘は既存ツールに任せ、本プロダクトは「読む前」に特化する。

## 11. スコープ

### MVP

- GitHub App（webhook / polling）、単一コンテナ、ファイルストア
- バックエンド: `claude-cli`・`codex-cli`・`gemini-cli`、フォールバック用に API 1 種以上
- ボード: ヘッダ、サマリ（Why/方針/What/影響）、PR 説明との乖離、読むべき箇所＋ノイズ内訳、リスクシグナル（決定的なもの中心）、モジュール依存の差分図
- sticky コメント、`/storyboard` コマンド、`.pr-storyboard.yml`
- 閲覧認証: `signed-url` と `none`

### 次段階

- `github-oauth` 認証、S3 互換ストア
- 処理フロー／シーケンス図、過剰実装シグナルの拡充
- push 間差分（「前回のボードから何が変わったか」）
- 各主張への 👍/👎 フィードバック（JSONL に追記。精度計測用）
- GitLab アダプタ

### やらないこと

- インラインのコード指摘、自動修正、承認・マージの自動化、ユーザ管理・課金基盤
